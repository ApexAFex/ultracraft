# Наполнение: что есть в Minecraft 26.3, что есть у нас и как закрывать разрыв

До сих пор работа шла по принципу «что мешает играть»: сначала байты в сокете, потом
картинка, потом ломание и инвентарь. Этот файл меняет мерку: цель — **наполнение**, то есть
игрок, зашедший на обычный сервер 26.3, должен увидеть там то же, что в оригинале.

Два правила, из которых всё вытекает:

1. **Сравниваем контент, а не внутренние решения.** Нас интересует, что видит и делает
   игрок. Как это устроено внутри — наше дело, и сомнительные оптимизации оригинала мы
   повторять не обязаны (см. [часть 4](#часть-4-что-мы-намеренно-не-копируем)).
2. **Совместимость не обсуждается.** Любое наполнение делается так, чтобы клиент продолжал
   играть на ванильном сервере по протоколу 777 без модов и плагинов (см.
   [часть 5](#часть-5-совместимость-что-нельзя-ломать)).

## Главное, что меняет взгляд на задачу

Мы пишем **клиент**, а не игру. Мир, мобы, редстоун, рост растений, лут, урон и торговлю
считает сервер; клиент только показывает результат и отправляет намерения игрока. Поэтому
половина «контента» приходит к нам по сети уже готовой.

| Слой | Кто его делает | Что это значит для нас |
|---|---|---|
| Генерация мира, структуры, биомы | сервер | приходит чанками, уже видно (блоками) |
| Мобы, их ИИ, урон, дроп | сервер | сущности и их движение приходят по сети |
| Редстоун, двери, поршни | сервер | результат приходит как `Block Update` |
| Рост растений, фермы, рыбалка | сервер | видно как смена состояний блоков |
| Форма блоков, модели, текстуры | клиент | **надо рисовать самим** |
| HUD, экраны, чат, звук | клиент | **надо делать самим** |
| Анимации, частицы, небо, свет | клиент | **надо делать самим** |

Отсюда неожиданный вывод: **редстоун у нас уже работает** — дверь открывается, поршень
двигает блоки, потому что это присылает сервер. Не работает клиентская часть: рычаг
нарисован кубом, щелчка не слышно, поршень не двигается плавно. Так же с фермами: пшеница
растёт, но выглядит кубом.

### 1.2. Блоки — 1286, состояний — 35 723

Блок — это не «кубик с текстурой», а набор **состояний**: у ступеней наклон и половинка, у

0–15. Состояний в игре в 28 раз больше, чем блоков, и именно они приходят в чанке.

Крупные семьи:

- **дерево** — 13 наборов (дуб, ель, берёза, тропическое, акация, тёмный дуб, мангровое,
  вишня, бледный дуб, тополь, бамбук, багровое, искажённое), у каждого брёвна, доски,

- **руды** — 18 (уголь, железо, медь, золото, редстоун, лазурит, алмаз, изумруд, кварц,

### 2.2. Приходит по сети, но не используется

Это самый дешёвый источник наполнения: данные уже есть, их надо только прочитать.

| Данные | Где они | Что теряем сейчас |
|---|---|---|
| **Биомы** | палитра биомов в секции | трава одного цвета везде, нет цветов биома |
| **Содержимое блок-сущностей** | `Block Entity Data` | сундук, табличка, знамя, кровать — кубы |
| **Метаданные сущностей** | `Set Entity Data` | нет здоровья, поз, вариантов, имён мобов |
| **Компоненты предметов** | patch в стеке | предметы с компонентами показываются как «?» |
| **Открытие меню** | `Open Screen` | сундук и верстак не открываются |
| **Звук** | `Sound` / `Entity Sound` | тишина |
| **Частицы** | `Particle` | нет дыма, искр, брызг |

### 2.3. Чего нет вовсе

- **Брони, воздуха и иконок эффектов.** Здоровье, голод и опыт уже на экране, но броня
  и эффекты зелий не выводятся.
- **Мобов с моделями.** Любая сущность, кроме игрока, — бирюзовая коробка.
- **Анимаций сущностей** (кроме ходьбы игрока) и **частиц**.
- **Форм блоков.** Все блоки — кубы: ступени, плиты, заборы, двери, панели, факелы,
  растения, рельсы, кровати.
- **Прозрачности.** Вода непрозрачная, листва сплошная, стекло как камень.

### 2.5. Почему «кубы» — это не мелочь

Все 1286 блоков приходят состояниями, и клиент рисует каждое состояние кубом. Для камня,
досок, земли это правильно. Но не-кубических блоков в игре больше половины (по именам —
660 из 1286), и там куб не «упрощение», а ошибка, которую видно сразу:

| Блок | Как выглядит у нас | Почему это ломает игру |
|---|---|---|
| Ступени, плиты | целый куб | нельзя подняться без прыжка, лестницы в домах не работают |
| Двери, люки | куб | дверь не открыть, дом без входа |
| Заборы, стены | куб | забор — сплошная стена |
| Факелы, цветы, трава | куб | нельзя пройти, хотя должны пропускать |
| Вода, лава | непрозрачный куб | воды не видно насквозь, а держать она не может: в ней только тонешь |
| Стекло, листва | непрозрачный куб | из дома не видно улицы |
| Рельсы, ковры | куб | по рельсам не пройти — они стена |

Поэтому «формы блоков» стоят в плане выше, чем, например, мобы: они влияют на то, можно ли
вообще ходить по миру.

## Часть 4. Что мы намеренно не копируем

Мы обязаны **читать** ванильный формат на проводе, но не обязаны **хранить и считать** так же.
Ниже — решения оригинала, которые выглядят как оптимизация, но для нас создают сложность без
выгоды.

| Решение оригинала | Почему не копируем | Что делаем вместо |
|---|---|---|
| Палитровые контейнеры и битовая упаковка (`PalettedContainer`) в памяти | экономит байты, но усложняет каждое чтение блока | читаем с провода, храним простым массивом `int` |
| Пересборка меша по секциям 16³ | нужна для огромных миров и стриминга по секциям | меш на чанк: правка блока пересобирает один чанк |
| Собственный световой движок (распространение света) | сложен и легко расходится с сервером | берём массивы света из чанка — сервер уже посчитал |
| Запекание всех моделей при старте (`ModelManager`, `BlockModelShaper`, multipart) | десятки тысяч JSON и секунды загрузки | ленивая интерпретация моделей по требованию |
| `DataTracker` на все поля сущности | 100+ индексов, из которых нужны единицы | читаем только те поля, что показываем |
| Хеши предметов в клике | нужны только чтобы не слать лишний пакет | шлём неверный `stateId`, получаем полное меню |
| Формат региона (Anvil) для сохранения мира | это забота сервера, клиент ничего не хранит | не сохраняем мир |
| `ItemRenderer` со спецслучаями для каждого предмета | сотни частных случаев | общие модели, исключения — по мере надобности |
| Шрифт с unifont и страницами глифов | нужен для всех языков сразу | простой атлас, расширяем под нужный язык |
| `SoundEngine` с 1991 событием и `sounds.json` | тяжёлая подсистема на старте | играем по имени события, грузим по требованию |
| GUI на виджетах и 9-slice | универсально, но много кода | простые квады и свой минимальный слой |
| Клиентское предсказание (установка, ломание, движение) | расходится с сервером и даёт «резинку» | ждём ответ сервера (уже так) |

- **Версия зафиксирована**: 26.3, протокол 777. ID пакетов — только в `Protocol777`.
- **Формат провода ванильный**: чанки, реестры, NBT без имени, стеки с компонентами.
  Мы можем не понимать часть данных, но обязаны не сбивать поток (length-delimited пакеты).
- **Сервер — истина**: позиция, инвентарь, ломание, время. Клиент не спорит с сервером.
- **20 тиков**: движение и `Client Tick End` идут по тикам, не по кадрам.
- **Без модов и плагинов**: вход на обычный сервер с `online-mode=true` — обязательная
  проверка каждого этапа.
- **Проверка без глаз**: `--demo`, `world --at`, RCON, второй клиент. Скриншот — дополнение,
  а не доказательство.

[content-appendix.md](content-appendix.md) — полные списки из данных игры: все блоки и

биомы, частицы, правила игры и атрибуты.

Файл генерируется, а не пишется руками:

```powershell
java -DbundlerMainClass=net.minecraft.data.Main -jar tools/server/server.jar --reports
node tools/build-content-report.js
```

Он описывает **оригинал**, а не наш клиент, поэтому его можно обновлять независимо от кода.
