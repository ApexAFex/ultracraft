# Заметки о протоколе 777 (Java Edition 26.3)

Всё ниже выяснено на живом ванильном сервере 26.3 и проверено кодеком проекта.
Помогает не наступить на те же грабли второй раз.

## Вход

- `Login Success` содержит **Game Profile + Session ID (UUID)** — двух полей, а не только профиль.
- `Set Compression` может прийти до `Login Success`; после него всё сжато zlib.
  Ванильный сервер ставит порог 256, пакеты меньше — «stored» с длиной 0.
- Причина отказа в состоянии `login` — **JSON-строка**, а в `configuration`/`play` — **NBT-компонент**.
  Обрабатывать нужно оба варианта.

## Подтверждение телепорта

`Confirm Teleportation` (serverbound) с 1.21.2 требует повторить не только `Teleport ID`,
но и **X, Y, Z, Yaw, Pitch** из запроса. Иначе сервер рвёт соединение с
`Failed to decode packet 'serverbound/minecraft:accept_teleportation'`.

## Движение игрока

- Позиция — **абсолютная**, Y — уровень ног (не глаз).
- С 1.21.2 движение разбито на четыре пакета: `Set Player Position` (0x1E),
  `Set Player Position and Rotation` (0x1F), `Set Player Rotation` (0x20),
  `Set Player Movement Flags` (0x21). Последнее поле каждого — байт флагов:
  бит 0 «стоит на земле», бит 1 «упёрся в стену».
- `Client Tick End` (0x0D) закрывает клиентский тик, полей нет. Сервер ждёт его **до**
  нового пакета позиции, иначе кик `Invalid move player packet received`. Поэтому поток
  начинается с пустого `Client Tick End`, а дальше на каждый тик идёт не больше одного
  пакета движения плюс разделитель.
- Тиков в секунду — 20, и физику с отправкой надо вести именно с этой частотой, а не с
  частотой кадров: `Client Tick End` ванильный сервер считает, чтобы понять, что клиент
  загрузился (первый тик игрока — после 60 таких пакетов).
- Раз в 20 тиков позиция отправляется заново, даже если игрок стоит: иначе сервер теряет
  представление о том, где мы.
- `Player Loaded` (0x2C) — «террейн на экране», снимает ожидание загрузки на сервере.

## Таблица id и как её проверять

Единственное место с номерами пакетов — `Protocol777`. Сверять их удобно по
`data/pc/<версия>/protocol.json` из PrismarineJS/minecraft-data: там id и поля в
машиночитаемом виде. Для 26.3 этого файла ещё нет, ближайший — 26.1 (протокол 774).

```powershell
Invoke-WebRequest -UseBasicParsing `
  -Uri "https://raw.githubusercontent.com/PrismarineJS/minecraft-data/master/data/pc/26.1/protocol.json" `
  -OutFile tools/mcd/protocol-26.1.json
```

Разница 26.1 → 26.3: **один пакет вставлен перед `Keep Alive`**, из-за чего всё начиная с
него сдвинулось на +1 (keep alive 0x2C → 0x2D, chunk data 0x2D → 0x2E, login 0x31 → 0x32,
update entity position 0x35 → 0x36, synchronize position 0x48 → 0x49, remove entities
0x4D → 0x4E). Пакеты до этого места совпадают. Проверять так: id, которые уже работают на
живом сервере, служат якорями — остальные не могут сдвинуться, не сдвинув якоря.

## Ломание блоков: коды действий и как сервер сам о них рассказывает

`Player Action` (serverbound 0x29) — это `status` (VarInt), позиция, грань (байт), `sequence`
(VarInt). Коды `status` берутся из порядка констант в enum сервера, и **в 26.x порядок не тот,
что в старых описаниях протокола**:

| Код | Действие |
|---|---|
| 0 | `START_DESTROY_BLOCK` |
| 1 | `CHANGE_DESTROY_DIRECTION` |
| 2 | `ABORT_DESTROY_BLOCK` |
| 3 | `STOP_DESTROY_BLOCK` |

Раньше `CHANGE_DESTROY_DIRECTION` шёл после `STOP`, поэтому «остановить копание» было `2`.
Клиент, который шлёт старое `2`, вместо окончания копания **отменяет** его: блок остаётся,
ошибок нет. Мгновенные блоки (трава, цветы) при этом ломаются, потому что сервер уничтожает
их на `START` — из-за этого ошибка долго не проявлялась.

Сервер считает прогресс сам, по тикам: `speed / hardness / (30 если инструмент подходит
иначе 100)` за тик, где `speed` — скорость руки или инструмента. Блок ломается, когда
прогресс достигает 1.0; `STOP` — это просьба «доделай сейчас», и сервер принимает её только
если его собственный прогресс дошёл до 0.7. Если отпустить раньше, сервер не отменяет
копание, а планирует «отложенное» разрушение и всё равно доделывает его через несколько
тиков. Поэтому клиенту правильно **держать кнопку, пока блок не исчезнет**, а не отпускать
по своей оценке времени.

Проверить это можно логом самого сервера: он умеет печатать вердикт по каждому пакету.
Флаги — `-DMC_DEBUG_ENABLED=true -DMC_DEBUG_BLOCK_BREAK=true` (префикс системных свойств
`MC_DEBUG_`), плюс уровень `DEBUG` для `net.minecraft.server.level.ServerPlayerGameMode`.
Удобная обёртка:

```powershell
.\tools\server-start.ps1 -Restart -DebugBlocks
```

В логе появятся строки `Server ACK <sequence> <pos> <принято> <причина>`, где причина —
`actual start of destroying`, `destroyed`, `aborted destroying`, `too far`, `spawn protection`
и т.п. Это и есть ответ на вопрос «почему не ломается», без гадания по пакетам.

## Инвентарь: id, слоты и предметы

Пакеты (проверены на живом сервере, id из `GameProtocols` самого jar и из
`reports/packets.json` генератора данных):

| Направление | Пакет | id |
|---|---|---|
| clientbound | `container_set_content` (всё содержимое) | `0x12` |
| clientbound | `container_set_slot` (один слот) | `0x14` |
| clientbound | `set_held_slot` (выбранный слот хотбара) | `0x6B` |
| clientbound | `set_player_inventory` (слот инвентаря) | `0x6E` |
| serverbound | `set_carried_item` (сменить слот) | `0x36` |

**Слоты адресуются двумя разными способами.** `container_set_content` и `container_set_slot`
описывают **меню** игрока (`InventoryMenu`): крафт, броня, основной инвентарь, хотбар — и там
хотбар это `36..44`. А `set_player_inventory` описывает сам инвентарь, где хотбар `0..8`.
Первая версия клиента смешала их и положила предметы «на 36 слотов мимо руки» — ошибка тихая,
предметы приезжают, просто не в руку.

`set_carried_item` несёт номер слота как **short**, а не VarInt.

**Стек предмета** — это `count` (VarInt, 0 = пусто), `item id` (VarInt) и `DataComponentPatch`:
два счётчика (добавленные, удалённые) и тела компонентов. У каждого компонента собственный
кодек, поэтому длину тела без него не узнать: клиент читает точные `count`/`id` только при
пустом patch (обычная стопка блоков), а иначе показывает предмет как неизвестный. Зато
`container_set_content` в таком случае отбрасывается целиком — пакеты length-delimited, и
дальше разбор не едет по мусору.

**Реестр предметов по сети не приходит** (в отличие от измерений и биомов): id предметов
встроены в клиент. Таблица генерируется из данных самой игры:

```powershell
java "-DbundlerMainClass=net.minecraft.data.Main" -jar tools/server/server.jar --reports
node tools/build-item-table.js      # data/items-777.tsv
```

Тот же запуск даёт `reports/packets.json` — полный список пакетов с id. Если нужно проверить
id по jar, есть `tools/protocol-ids.java`: он просит список у самого сервера через
`GameProtocols`, а не парсит байткод.

## Клик по контейнеру: почему можно не считать хеши

`Container Click` (serverbound `0x12`) — единственный способ переместить предмет. Поля:
`containerId` (VarInt), `stateId` (VarInt), `slot` (short, слот **меню**), `button` (byte),
`containerInput` (VarInt: 0 `PICKUP`, 1 `QUICK_MOVE`, 2 `SWAP`, …), `changedSlots`
(VarInt-карта «слот → `HashedStack`») и `carriedItem` (`HashedStack`, опциональный).

`HashedStack` — это хеш предмета, а не сам предмет: клиент присылает, что он **ожидает**
увидеть, а сервер сверяет. Читая `ServerGamePacketListenerImpl.handleContainerClick`, видно
главное: сервер сначала применяет клик у себя (`menu.clicked(...)`), потом лишь записывает
наши хеши (`setRemoteSlotUnsafe`, `setRemoteCarried`), и если `stateId` не совпал — шлёт полное
состояние меню, иначе только изменившиеся слоты.

Отсюда два вывода:

1. **Хеши считать не обязательно.** Клик с пустыми `changedSlots` и пустым `carriedItem`
   применяется; сервер просто может не прислать то, что, по его мнению, у нас уже есть.
2. **Чтобы курсор всегда был точным, шлите неверный `stateId`** (например `-1`): тогда на
   каждый клик приходит полное меню вместе с курсором. Один лишний пакет на клик — дешевле,
   чем реализовывать хеши компонентов.

Курсор приходит двумя путями: отдельным пакетом `set_cursor_item` (clientbound `0x62`) и
**последним полем** `container_set_content` — после 46 слотов, а не как слот `-1`.

Слоты меню: `0` результат крафта, `1..4` сетка 2×2, `5..8` броня, `9..35` инвентарь,
`36..44` хотбар, `45` оффхенд. В `set_player_inventory` и `set_held_slot` нумерация другая —
хотбар `0..8`, см. раздел про инвентарь.

Крафт — это те же клики: взять стопку из хотбара, положить в сетку, забрать результат из
слота `0` (сервер сам спишет ингредиенты и пересчитает результат).

## Полёт и кик за полёт

- Разрешение летать приходит отдельным пакетом `Player Abilities` (clientbound 0x41):
  байт флагов (0x01 неуязвимость, 0x02 летит, 0x04 **можно летать**, 0x08 творческий),
  затем скорость полёта и скорость ходьбы (по `float`).
- Если бита «можно летать» нет, сервер выживания через ~80 тиков кикает:
  `Flying is not enabled on this server` (`multiplayer.disconnect.flying`). Перед этим он
  ещё пишет в лог `Player <ник> standing on air - force-sending blocks below`.
- Причина кика — **ключ перевода**, а не текст: `multiplayer.disconnect.duplicate_login`,
  `multiplayer.disconnect.flying` и т.п. Клиент обязан перевести их сам; иначе игрок видит
  голый ключ.

## Углы: yaw и pitch считаются в другую сторону

Наш рендер держит `forward = (sin(yaw)·cos(pitch), sin(pitch), cos(yaw)·cos(pitch))`:
yaw 90° смотрит в +X, положительный pitch — вверх. В протоколе наоборот —
`(-cos(pitch)·sin(yaw), -sin(pitch), cos(pitch)·cos(yaw))`: yaw 90° смотрит в −X,
положительный pitch — вниз. Поэтому на провод уходит `-yaw, -pitch`, иначе сервер считает,
что мы смотрим в другую сторону: его собственный `pick()` выбирает другой блок.

## Реестры

- Сетевой NBT **не имеет имени корневого тега** (с 1.20.2): `[type][payload]`, без строки имени.
  Чтение лишних двух байт сдвигает весь поток.
- `minecraft:block` — **встроенный** реестр: по сети он больше не приходит, содержимое
  фиксировано версией протокола. Клиент обязан знать таблицу состояний сам.
  Берём её из официального дата-генератора (`tools/build-block-table.js`).
- `minecraft:dimension_type` приходит по сети и даёт `min_y` и `height`;
  из `height` получается число секций чанка.

## Чанк

- Поле `Data` — **массив без префикса длины**: число секций = `height / 16`, а не поле пакета.
- Секция: `Block Count` (Short), **`Fluid Count` (Short, с 1.21.5)**, палитра блоков, палитра биомов.
- С 1.21.5 **длина массива данных палитры не передаётся**: считается из bits per entry и числа записей,
  значения упакованы без пересечения границ long.
- Секции идут снизу вверх; индекс внутри секции — `y * 256 + z * 16 + x`.
- Небо/свет идут после `Block Entities` и пока не разбираются.
- Проверка целостности: после секций в буфере должно остаться 0 байт.

## HUD: здоровье, голод, опыт и смерть

- `Set Health` (0x6A): `float health`, `VarInt food`, `float saturation` — всё одним пакетом.
- `Set Experience` (0x69): `float progress` (0..1), `VarInt level`, `VarInt total`.
- Отдельного «ты умер» для экрана не нужно: сервер выставляет здоровье в 0 и **перестаёт
  присылать чанки**. `Player Combat Kill` (0x45) несёт причину смерти NBT-компонентом —
  пока не разбираем, экран показывает нейтральное «YOU DIED».
- `Respawn` (0x54) — сервер подтвердил возрождение, после него снова идут чанки и телепорт.
  Клиент просит возрождение пакетом `Client Status` (0x0C) с действием 0.
- Спрайты HUD лежат **не** в старом `textures/gui/widgets.png`, а по одному файлу:
  `assets/minecraft/textures/gui/sprites/hud/…` (`hotbar`, `hotbar_selection`, `crosshair`,
  `heart/full`, `heart/half`, `heart/container`, `food_full`, `food_half`, `food_empty`,
  `experience_bar_background`, `experience_bar_progress`). Читаются из jar версии, как и
  текстуры блоков.
- У пробела в `ascii.png` нет ни одного пикселя, поэтому «ширина + 1» даёт 1 пиксель и слова
  слипаются. В ванили шаг пробела фиксированный — 4 пикселя; его и берём.
- HUD рисуется поверх сцены: своя ортопроекция (`uScreen`), `y` растёт вниз, глубина и
  отсечение граней выключены, прозрачность включена.

## Окружение

- Ванильный сервер 26.3 требует **Java 25** (на 21 падает с `UnsupportedClassVersionError`).
- `white-list` у сервера 26.3 по умолчанию **включён** — для локальных тестов его нужно выключить.
