# С чего начать переписывание Minecraft

Рабочая цель: свой современный код, официальные функции, доступ к мультиплееру, без модов.
Целевая версия: **Java Edition 26.3, протокол 777** (актуальный релиз на 2026-11).

**Решение зафиксировано (2026-11-18):** вариант **A — совместимый клиент**, стек **Kotlin 2.1 / JDK 21**.
См. [ADR-0001](adr/0001-product-client.md) и [ADR-0002](adr/0002-stack-kotlin-jvm.md).

**Прогресс:**

- ✅ **E1** — Server List Ping против живого сервера.
- ✅ **E2** — вход: login → configuration → `Join Game` разобран, сервер пишет «joined the game».
- ✅ **E3** — мир: чанки, палитровые секции, таблица блоков, ASCII-карта местности.
- 🟡 **E4** — вход через Microsoft: код готов (device code, Xbox Live, шифрование),
  заявка в Mojang подана, ждём одобрения приложения.
- 🟡 **E5** — картинка: CPU-рендер в PNG и окно на GPU (OpenGL 3.3, текстуры из jar);
  свет и небо — следующий шаг.
- ✅ **Геймплей и мультиплеер** — ходьба/прыжок/полёт с коллизиями, ломание и установка
  блоков, приём сущностей с интерполяцией, отправка своего движения на 20 тиках: другие
  игроки видят нас идущими, сервер сохраняет позицию между сеансами.

---

## 0. Короткий ответ

1. **Не начинай с рендера, генерации мира и редстоуна.** Начни с протокола: это единственный внешний контракт, который нельзя придумать самому, и он общий для клиента и сервера.
2. Раздели проект на три слоя: `protocol` (байты) → `world/game` (модель) → `render/ui` (картинка). Первые два — headless и тестируемые без окна.
3. Сначала **вертикальный срез без графики**: ping → login → join → чанк → шаг. 2–3 недели, и ты знаешь, жива ли затея.
4. Юридически: свой код — да, чужой jar и ассеты — нет. Ассеты читаются из установленной игры пользователя.
5. Что именно переписываем — **уже решено: вариант A, совместимый клиент** (см. §1 и ADR-0001).

## 1. Главная развилка: «переписать Minecraft» — это три разных проекта

| Вариант | Что получаешь | Что реально сложно | До «играбельного» |
|---|---|---|---|
| **A. Совместимый клиент** | заходишь на официальные и публичные серверы, свой рендер, свой UI | Microsoft-auth + подпись чата, воксельный рендер, физика и предсказание движения, ассеты | 6–12 мес силами одного |
| **B. Совместимый сервер** | официальный клиент заходит к тебе: мир, чат, блоки, игроки | генерация мира, редстоун, моб-ИИ, хранение, античит | 3–9 мес до «играем вдвоём» |
| **C. Ядро протокола (headless)** | библиотека/бот, общая база для A и B | почти ничего, но само по себе не игра | 3–5 недель |

**Решение:** выбран **A**. Стартовый срез при этом остаётся **C** — первые 2–3 недели (VarInt, NBT,
состояния соединения, шифрование, реестры, формат чанка) одинаковы для A и B, и эта работа
не пропадёт ни при каком исходе.

## 2. Честно про «код 2009 года»

Это важно поправить, иначе будешь модернизировать не то.

- 2009 — это Classic/Indev. **Современный Minecraft — не код 2009 года**: клиент переписан на Netty в 1.7, «flattening» блоков и предметов в 1.13, мир на секциях 16³ с палитрами в 1.18, состояние `configuration` в протоколе с 1.20.2, реестры (блоки, предметы, биомы, измерения) стали передаваться по сети с 1.20.5, а после 1.21.11 Mojang перешла на нумерацию `26.x`.
- Что в игре действительно «легаси» и что стоит не тащить в свой код:
  - один гигантский тик-луп, где смешаны физика, ИИ, сеть и рендер-подготовка;
  - глобальное состояние и синглтоны вместо явных зависимостей;
  - жёсткая связка «логика знает про рендер»;
  - почти нет юнит-тестов на игровую логику;
  - поведение задано кодом там, где его можно задать данными.
- Полезный факт: в 1.21.11 Mojang выпустила **unobfuscated** сборки — эталон стал читаемым. Читать для понимания поведения — нормально; **копировать код в свой — нельзя** (см. §3).

Вывод: «современный вид» = слои, явные зависимости, данные вместо хардкода, тесты — а не другой язык ради языка.

## 3. Юридическая рамка (коротко и по делу)

- Реализация протокола по документации — обычная практика: [Minestom](https://minestom.net:2096/docs/what-is-minestom) прямо заявляет «without any code from Mojang», [Pumpkin](https://docs.pumpkinmc.org/) написан на Rust с нуля. Прецедентов запрета такой интероперабельности нет.
- **Нельзя**: распространять `client.jar`/`server.jar` и любые ассеты (текстуры, звуки, шрифты, модели, датапаки), продавать под именем Minecraft, вставлять в свой код фрагменты декомпилированного кода.
- **Можно и нужно**: читать ассеты и данные из **установки пользователя** (`.minecraft/assets`, индексы, objects по SHA-1) во время работы. Ничего не бандлишь — ничего не нарушаешь.
- Бренд: своё имя, свой логотип, дисклеймер «не связан с Mojang». Non-commercial, пока не поговоришь с юристом.
- Я не юрист. Если проект станет коммерческим — консультация обязательна.

## 4. Стек: решение и обоснование

**Kotlin 2.x на JDK 21 LTS + Gradle. Рендер позже — LWJGL 3, OpenGL 4.6.**

Почему так:

- Знание протокола живёт в Java-мире: документация, Minestom как работающий референс, сам эталон на JVM — можно запускать рядом и сравнивать пакеты.
- Один язык на всё: сеть, мир, логика, позже рендер (LWJGL — это Java-биндинги).
- Скорость итерации важнее пиковой производительности: 24 ГБ RAM и 20 TPS JVM держит с запасом, а JFR даёт профилирование бесплатно.
- Твоё железо (Intel Ultra 7 255H, Intel Graphics) спокойно тянет OpenGL 4.6; для воксельного рендера этого достаточно.

Альтернативы, если захочешь иначе:

- **Rust** — современнее и быстрее, есть [Valence](https://github.com/valence-rs/valence) и Pumpkin как референс, но протокол придётся выводить самому, а итерации по геймплею медленнее. Берёшь, если цель — «максимально современно», а не «быстро увидеть игру».
- **C#** — экосистемы под MC практически нет, всё с нуля.
- **TypeScript** — только для тулинга (скрипты дампа пакетов, оракул), не для самой игры.

Чего сейчас нет на машине: `git`, JDK, Rust. Ставится за 10 минут (§7).

## 5. Архитектура: что зафиксировать до первой строки кода

| Слой | Ответственность | Что не должен знать |
|---|---|---|
| `protocol` | байты, VarInt, типы данных, NBT, кодирование/декодирование пакетов | про мир, игроков и рендер |
| `net` | соединение, состояния (`handshake → status/login → configuration → play`), сжатие, шифрование, keep-alive | про содержимое мира |
| `world` | чанки 16³-секции, палитры, блоки, биомы, свет, хранение | про сеть и рендер |
| `game` | тик 20 TPS, сущности, игрок, инвентарь, чат, события | про байты и картинку |
| `assets` | чтение ресурсов из установки игрока, индексы, модели | про логику |
| `render`/`ui` | окно, шейдеры, ввод, HUD | про сеть и правила игры |

Пять правил, которые сэкономят месяцы:

1. `protocol` не импортирует ничего из `world/game`. Пакеты — это DTO, не бизнес-объекты.
2. Никаких синглтонов и глобального состояния: зависимости через конструктор.
3. Игровая логика — **фиксированный шаг 20 TPS**. Паритет физики с ванилой возможен только на тех же тиках.
4. Реестры (блоки, предметы, биомы, измерения) приходят **по сети** — не хардкодь числовые ID. С 1.20.5 сервер присылает их в состоянии `configuration`, и это твой главный источник истины о содержимом.
5. Всё, кроме `render`/`ui`, обязано работать без окна и иметь тесты.

Решения, которые можно принять сейчас (значения по умолчанию):

- версия-цель фиксируется: **26.3 / 777**, обновление — осознанным апгрейдом раз в несколько месяцев;
- сеть: **Netty** (проверенная, асинхронная), не самописный NIO;
- сериализация: `kotlinx.serialization` для JSON, свой кодек для NBT;
- UI позже: `imgui-java`, чтобы не писать GUI-фреймворк;
- ECS не нужен на старте: обычные классы + пулы объектов; ECS добавишь, если упрёшься;
- рендер: OpenGL 4.6, а не Vulkan — Vulkan ты будешь отлаживать месяц до первого куба.

## 6. Первые 14 дней: шаги с критериями приёмки

| Этап | Дни | Что делаешь | Готово, когда (DoD) |
|---|---|---|---|
| **E0. Фундамент** | 1–2 | `git init`, структура модулей, CI, ADR-0001 (стек), локальный ванильный сервер 26.3 в `online-mode=false` | `git push` работает; сервер стартует; в его `version.json` `protocol_version: 777`; CI зелёный на пустом проекте |
| **E1. Кодек + ping** | 3–4 | VarInt/VarLong/String/UUID/Position/NBT + тесты; `Handshake` + `Status Request`, парсинг JSON-ответа | твоя программа печатает MOTD, версию и число игроков живого сервера |
| **E2. Login (offline)** | 5–7 | `Login Start` → `Login Success`, переход в `configuration`: `Registry Data`, `Feature Flags`, затем `play`: `Login (Join Game)` | сервер в логе пишет «player joined», ты распарсил Join Game и реестры |
| **E3. Мир** | 8–11 | `Chunk Data and Update Light`: палитровые секции, heightmaps, block entities; реестр блоков → `id → имя` | ASCII-карта 20×20 чанков вокруг спавна печатается в консоль и совпадает с миром |
| **E4. Online-mode** | 12–14 | Microsoft device-code flow → Xbox Live → XSTS → Minecraft services → `Encryption Request/Response` (AES + RSA) | ты зашёл на публичный online-mode сервер, headless-клиент в списке игроков |
| **E5. Первый пиксель** | дальше | загрузка ассетов из установки игры: `assets/indexes/*.json` → objects, `blockstates` → `models` → текстуры; один чанк в окне LWJGL | окно с одним чанком, текстуры из твоей копии игры |

Для E4 нужен **бесплатный Azure app registration** (device code flow, scope `XboxLive.signin`) — это отдельный шаг, который нельзя обойти: без client id Microsoft-логин не начать.

### Честно про оценки

Числа в колонке «Дни» — интуиция, а не расчёт: за ними нет ни декомпозиции, ни замеров,
и они предполагают человека, печатающего руками. Фактические замеры по завершённым шагам
(по времени коммитов):

| Шаг | План | Факт |
|---|---|---|
| E1 — кодек и ping | 2 дня | ~23 мин |
| E2 — вход на сервер | 3–4 дня | ~36 мин |
| E3 — чанки и карта | ~4 дня | ~37 мин |

Поэтому дальше считаем не днями, а шагами: «сделано за N минут, осталось M шагов».
Оценка «когда будет окно с миром» честно даётся только после E3, когда станет видно
реальную стоимость разбора чанков.

Ключевой приём: **ванильный сервер — твой оракул**. Не угадывай байты, а пиши дамп-режим: логируй все входящие пакеты в hex + разобранный вид, и сравнивай со спецификацией на [minecraft.wiki/w/Java_Edition_protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets). Машиночитаемый справочник — [minecraft-data](https://github.com/PrismarineJS/minecraft-data) (PrismarineJS).

## 7. Первый день: конкретные команды

```powershell
winget install --id Git.Git -e
winget install --id EclipseAdoptium.Temurin.21.JDK -e
# проверка
git --version
java -version
```

Локальный сервер: скачать `server.jar` с minecraft.net для 26.3, положить в `tools/server/`, рядом `eula.txt` с `eula=true`, в `server.properties` — `online-mode=false`, `level-type=flat`, `spawn-protection=0`. Запуск: `java -Xmx2G -jar server.jar nogui`.

Структура репозитория на старте:

```
docs/            START-HERE.md, adr/
protocol/        байты и пакеты
net/             соединения и состояния
tools/           дамп пакетов, оракул, server/
```

## 8. Где такие проекты умирают

- **Рендер раньше протокола.** Красивые скриншоты без соединения — это не Minecraft, а демка воксельного движка.
- **«Сначала сделаю движок, потом игру».** Движок без потребителя обрастает неверными абстракциями.
- **Паритет редстоуна/моб-ИИ как цель v1.** Это спецификация на тысячи поведений; годами, без видимого прогресса.
- **Перфекционизм по физике.** Сначала «не резинит», паритет — потом.
- **Mods/plugin API слишком рано.** Ты его правильно отложил. Но не путай «нет модов» с «нет расширяемости»: сделай ядро data-driven (реестры, JSON-описания), и лёгкая расширяемость появится сама.
- **Нет демонстрируемого среза каждые 2 недели.** Правило: раз в две недели что-то работает end-to-end, пусть маленькое.

## 9. Чего сознательно не делаем (non-goals)

Bedrock-протокол, Realms, Marketplace, скины и плащи, микротранзакции, телеметрия, полный паритет перевода/доступности, поддерживаемый API для модов. Всё это — после «играбельного v0.1».
