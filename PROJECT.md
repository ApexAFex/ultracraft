# ultracraft (майн+) — заметки по проекту

Документ для человека и для агента: что здесь есть, **почему** сделано именно так и что
делать дальше. Перечитывать перед крупными изменениями — часть решений неочевидна и
легко «улучшается» обратно в проблему.

## Что это

Клиент Minecraft: Java Edition, написанный с нуля на Kotlin/JVM: свой протокол, свой мир,
свой рендер. Официальные функции, доступ к мультиплееру, **без поддержки модов**.

Целевая версия зафиксирована: **26.3, протокол 777**. Не «последняя», а именно эта:
номер протокола и ID пакетов меняются каждый релиз, и привязка к «последней» превращает
любой апдейт в переписывание.

Замысел шире «поиграть»: это способ пройти путь игры целиком — от байтов в сокете до
пикселя на экране — и получить работающий клиент, а не мод к чужому. Отсюда требования,
которые не видны в игре: протокол отдельно от мира, мир отдельно от рендера, всё
тестируемое без окна и без видеокарты.

Проект не связан с Mojang и Microsoft. Код игры и её ассеты не распространяются: текстуры
читаются из установки игрока во время работы.

## Запуск и проверка

```powershell
.\gradlew.bat build                        # компиляция + 45 тестов — минимум перед «готово»
.\gradlew.bat :app:packageExe              # dist\ultracraft\ultracraft.exe (свой рантайм Java)
.\gradlew.bat :app:run --args="window"     # запуск из исходников
```

Команды клиента:

```
ultracraft.exe                окно: WASD, пробел, F — полёт, ЛКМ/ПКМ — блоки, Esc
ultracraft.exe world          карта мира текстом
ultracraft.exe view           карта мира в PNG (CPU-рендер)
ultracraft.exe watch          что двигалось в мире за N секунд (проверка «нас видно»)
ultracraft.exe ping <сервер>  список игроков
ultracraft.exe join           проверка входа без окна
ultracraft.exe login          вход через Microsoft (ждёт одобрения Mojang)
```

Локальный сервер (оракул протокола): `.\tools\server-start.ps1`. Нужен **JDK 25** —
сервер 26.3 на 21 не стартует; `white-list` у него включён по умолчанию, скрипт это правит.

**Проверка без рук.** У окна есть `--demo`: ломает и ставит блок, печатает координаты, идёт
вперёд первые пару секунд — в логе видно тики, позицию и число отправленных пакетов.
`--frames N --hidden --out файл.png` рисует N кадров и сохраняет снимок — так проверяется
рендер без участия человека. Присутствие в мире для других проверяется вторым клиентом:
`watch --seconds 20` показывает сущности, которые двигались, вместе с их UUID.

## Архитектура: байты → мир → кадр

```
Socket → FrameCodec → Packet → MinecraftClient (вход, реконфигурация)
                                     ↓
                         Session (состояние play, keep-alive)
                        ↙                    ↘
      поток сети: чанки, сущности        главный поток: физика, ввод, GL
             ↓                                    ↓
      World.addChunk (потокобезопасно)      MeshPipeline (15 потоков)
             ↓                                    ↓
      очередь мешей ──────────────────→ загрузка в видеопамять (≤16 за кадр)
```

| Модуль | Роль | Зависимости |
|---|---|---|
| `protocol` | VarInt, строки, NBT, палитры, фрейминг, zlib | нет |
| `net` | соединение, вход, реестры, мир, сущности, пакеты действий | `protocol` |
| `auth` | Microsoft → Xbox Live → Minecraft services, сессии | нет |
| `app` | CLI, физика, меши, OpenGL, exe | `net`, `auth` |

Правило: `protocol` не знает про мир, мир не знает про рендер.

## Решения, которые нельзя менять молча

**Версия и ID пакетов — в одном месте.** `Protocol777` — единственный файл с числовыми ID.
Они меняются между релизами; разбрасывать их по коду значит гарантировать тихую поломку
при апдейте.

**Реестр блоков больше не приходит по сети.** С 26.x `minecraft:block` — встроенный реестр.
Клиент обязан знать таблицу состояний сам, поэтому `data/blocks-777.tsv` генерируется из
официального дата-генератора (`tools/build-block-table.js`) и в git не попадает.
Попытка взять имена блоков из `Registry Data` — тупик: пакета с блоками просто нет.

**Сетевой NBT без имени корневого тега.** С 1.20.2 корневой compound идёт как
`[type][payload]`. Чтение лишних двух байт сдвигает весь поток; именно на этом сначала
разъехались реестры.

**У чанка нет поля «количество секций».** Число секций = `height / 16` из реестра
`dimension_type`. В секции есть `fluid count` (с 1.21.5), а длина массива палитры больше
не передаётся — считается из bits per entry. После секций в буфере обязан остаться ноль
байт: это дешёвая проверка, что формат не поехал.

**Меш на чанк, а не на мир.** Раньше весь мир был одним буфером: правка блока требовала
пересборки 250 тысяч граней — секунда зависания на каждый клик. Теперь правка пересобирает
один чанк, а загрузка в видеопамять идёт пачками (≤16 за кадр), чтобы не превратить
исправление рывка в новый рывок.

**Кадр не строит геометрию.** Сборка меша — обход 98 304 блоков на чанк; в кадре это
десятки миллисекунд. Работа вынесена в пул `mcplus-mesh`, кадр только загружает готовое.
Ускорение при этом около 3×, а не 15×: упор в аллокации и память, а не в ядра. Дальше
поможет не «ещё потоков», а меньше allocations.

**GL — только в главном потоке.** Контекст привязан к потоку; рабочие потоки считают
FloatArray, но ничего не загружают. Нарушение этого правила — падение драйвера, а не
исключение в логах.

**Мир потокобезопасен, но слабо.** `chunks` — `ConcurrentHashMap`, `setBlock` под
`@Synchronized`, чтение блоков без блокировок. Запись `int` в массив атомарна; рабочий
поток может увидеть устаревшее значение, и это допустимо: в худшем случае одна грань
появится на кадр позже.

**Текстуры — из установки игрока.** Читаются из `versions/<id>/<id>.jar` при запуске
(1301 слой), ничего не копируется в проект. Сначала я читал `assets/indexes/34.json` —
это старый индекс, там только иконки и панорамы; текстуры блоков современный Minecraft
держит в jar версии.

**Тонирование — при загрузке в видеопамять, а не при чтении.** Трава и листва в файлах
серые: цвет им даёт биом. Умножение в момент чтения до текстуры не доходило (картинка
оставалась серой); перенос в `GlTextures.uploadBuffer` решил вопрос.

**Мипмапы выключены, фильтр `NEAREST`.** Грань блока занимает 3–4 пикселя: производная UV
большая, сэмплер уходит на нижний уровень мипмапа, и мир становится серо-белым. Пиксельная
фактура — это уровень 0.

**UV считаются по грани.** Один общий набор UV поворачивал бока блоков. Сейчас: верх и низ
`u = x, v = 1 − z`; бока по X `u = z, v = 1 − y`; по Z `u = x, v = 1 − y`. `v = 1 − y`
нужен потому, что текстура грузится сверху вниз.

**Сервер выкинул — игрок должен это увидеть.** Консоль у упакованного exe своя, и Windows
закрывает её вместе с процессом: и падение, и кик выглядели как «игра просто исчезла».
Теперь любое аномальное завершение пишется в `ultracraft-error.txt` и показывается окном
(`CrashReport`), а `Session.send` никогда не бросает исключение в игровой цикл: он
запоминает причину в `closeReason`, игровой цикл по ней выходит, окно закрывается штатно.

**Полёт — только с разрешения сервера.** `Player Abilities` (clientbound 0x41) сообщает бит
«можно летать». Без него выживание кикает через ~80 тиков с `Flying is not enabled`; клиент
поэтому игнорирует F и говорит, что сервер не разрешает.

**Камера считает углы в другую сторону, чем протокол.** На провод уходит `-yaw, -pitch`:
иначе сервер выбирает `pick()`-ом другой блок и любое действие по блоку для него бессмысленно.

**Грани на границе незагруженного чанка рисуются.** Раньше сосед из ещё не приехавшего
чанка считался стеной, и у каждого пришедшего чанка пропадала полоса граней по периметру:
чанки мешатся по мере прихода, соседей в этот момент обычно нет. Вода вдали и поверхность
издалека выглядели как отдельные кубы в пустоте. Теперь «чанка нет» = «воздух»: двойные
совпадающие грани внутри мира не видны, а дыра в мир — видна.

**Мёртвый игрок не получает чанков.** Если игрок умер в прошлой сессии, сервер держит его
мёртвым и не стримит ему мир вообще: клиент видит «ни одного чанка». Лечится запросом
`Client Status: perform respawn` (0x0C, действие 0), который для живого игрока сервер
игнорирует; `WorldCollector` шлёт его сам, если за треть таймаута не пришло ни одного чанка.

**Физика: прижатие считается от пройденной точки.** Если прижимать от откатанной позиции,
стоящий ровно на высоте 63.0 персонаж каждый кадр «подпрыгивает» на целый блок. Проверка —
`--demo` или лог высоты: `y` должен стоять на месте.

**Мир идёт на 20 тиках, а не на кадрах.** Физика и отправка позиции вызываются только из
тика по 50 мс (не больше 5 тиков за кадр, остаток отбрасывается), а камера между тиками
интерполируется. Причина не в красоте: сервер принимает не больше одного пакета движения за
свой тик, а `Client Tick End` он вообще считает, чтобы понять, что клиент загрузился.

**Поток движения начинается с пустого `Client Tick End`.** Сервер требует разделитель
**до** нового пакета позиции, иначе кикает с `Invalid move player packet received`; первый
тик после входа всегда хочет что-то сказать (позиция спавна), поэтому разделитель уходит
вперёд, ещё до первого пакета.

**Позиция сервера — истина, а не догадка по рельефу.** Спавн берётся из `Synchronize
Position`, а не из «первый твёрдый блок сверху»: полблока разницы — и сервер правит каждое
движение. Телепорты сервера кладутся в очередь (`Session.pollTeleport`), игровой поток
забирает **последний**: цепочка старых исправлений протащила бы игрока через все прошлые
точки.

**Отправляется самый дешёвый пакет, описывающий изменение.** Движение и поворот — вместе
(`Set Player Position and Rotation`), только движение — `Set Player Position`, только
поворот — `Set Player Rotation`, сменилась опора под ногами — `Set Player Movement Flags`.
Раз в 20 тиков позиция отправляется заново, даже если игрок стоит: иначе сервер теряет
представление о том, где мы.

**Вход через Microsoft упирается в Mojang, а не в код.** Цепочка Microsoft → Xbox Live →
XSTS проходит целиком; `login_with_xbox` отвечает `403 Invalid app registration`, пока
приложение не одобрено через `aka.ms/mce-reviewappid`. Заявка подана. Код готов: как
одобрят, `mcplus login` заработает без правок.

**Упаковка в exe имеет три ловушки.** Нативные библиотеки LWJGL должны попасть в
зависимости (`org.lwjgl:lwjgl:$version:natives-windows`, запись без версии молча
игнорируется); jpackage не смотрит внутрь jar, поэтому DLL распаковываются рядом с exe;
`ImageIO` в урезанном рантайме падает на создании кеш-файла — лечится `setUseCache(false)`.

**Старт: сначала окно, потом мир.** Ждать загрузку мира целиком — это 6 секунд пустого
экрана. Сейчас ждём 25 чанков вокруг спавна (≤1.5 с), открываем окно, остальное приезжает
в потоке-читателе: 441 чанк в сцене через ~0.5 с после открытия.

## Текущее состояние

Работает: вход на offline-сервер, приём чанков и реестров, полный воксельный мир,
рендер на видеокарте с текстурами из игры, ходьба/прыжок/полёт с коллизиями, ломание и
установка блоков с подсветкой цели (пока как предсказание — см. долги), сущности с
интерполяцией движения, синхронизация изменений блоков с сервером, **отправка своего
движения на 20 тиках** (другие игроки видят нас идущими, сервер сохраняет нашу позицию),
стриминг мира, сборка exe.

| Метрика | Значение |
|---|---|
| Тестов | 59 (52 сеть/протокол + 7 геометрия мешей) |
| Слоёв текстур | 1301 (из `26.3.jar`) |
| Меши 441 чанка | 746–904 мс на 15 потоках, 2235 мс на одном |
| Сцена после открытия окна | 441 чанк за ~0.5 с |
| Размер exe-сборки | 157 МБ (130 МБ — Java) |

## Долги и ограничения

- **Сущности нарисованы коробками.** Движение уже интерполируется по `move_entity_pos`
  и `entity_position_sync` (linear), но «шаговые» пути (`path type = 1`) пропускаются,
  моделей и никнеймов нет.
- **Правки блоков сервер не подтверждает** — клиент меняет мир только у себя. Ломание
  отправляется как `Start Destroy` + `Stop Destroy` с задержкой в 2 тика, но сервер всё
  равно пишет `Mismatch in destroy block pos: 0,0,0 ↔ <наш блок>`: «начало копания» до него
  не доходит, и блок возвращается обратным `Block Update`. Сервер при этом подтверждает
  действие (`Acknowledge Block Change`) и дропа не появляется. Что именно сбрасывает
  `destroyPos` до нуля — **открытый вопрос**; разбирать вместе с настоящим прогрессом
  разрушения (нужна прочность блока из реестра) и удержанием ЛКМ.
- **Нет инвентаря, хотбара и чата.** Ставится всегда камень.
- **Мир только растёт** — далёкие чанки не выгружаются, при долгой игре память потечёт.
- **Нет сохранения мира** на диск и нет повторного подключения.
- **Модели блоков не читаются**: все блоки — кубы, ступени/двери/заборы выглядят кубами.
- **Свет и небо плоские**: затенение по нормали, без солнца, теней и освещения от блоков;
  вода непрозрачная, у листвы нет отсечения по альфе.
- **Только один тип входа**: `--online` есть, но заблокирован одобрением Mojang.
- **CPU-рендер (`view`) и GPU-рендер (`window`) — два разных кода.** Меши общие, шейдеры
  разные; CPU-путь оставлен как запасной и для скриншотов без дисплея.

## Ближайшие шаги

1. **Никнеймы и модели игроков** — сейчас коробки; тип сущности игрока в реестре 26.3 — 159.
2. **Шаговые пути** в `entity_position_sync` (`path type = 1`).
3. **Инвентарь и хотбар** — выбор блока вместо «всегда камень».
4. **Удержание ЛКМ** с прогрессом разрушения — иначе ломание в выживании не подтверждается.
5. **Выгрузка далёких чанков** — иначе память растёт бесконечно.
6. **Свет**: небо, солнце, освещение от блоков.
7. **Модели блоков** из `blockstates`/`models` в jar — ступени, заборы, двери.

  NBT без имени, нет числа секций, `Confirm Teleportation` требует эхо позиции.
- **2026-11-18.** GPU-рендер: OpenGL 3.3 через LWJGL, текстуры из jar, тонирование,
  UV по граням.
- **2026-11-18.** Геймплей: меши по чанкам, ломание/установка блоков, подсветка цели.
- **2026-11-18.** Многопоточность: пул мешей, поток чтения сети, потокобезопасный мир,
  стриминг чанков.
- **2026-11-18.** Движение сущностей (`move_entity_pos`: `properties >>> 1` — число шагов,
  дельты fixed-point /4096) и чтение `Block Update` в игровом цикле со пересборкой чанка.
- **2026-11-18.** Отправка своего движения: тик 20 Гц вместо кадров, `Client Tick End`,
  четыре пакета позиции/поворота, `Player Loaded`, спавн из `Synchronize Position`, очередь
  телепортов. Проверено двумя клиентами: наблюдатель увидел сущность `type=159` с UUID
  ходящего клиента, прошедшую 8.0 блоков, а сервер после переподключения вернул ровно ту
  позицию, куда клиент дошёл (`-61.71, 64.00, 40.41`). Заодно исправлено ломание: сервер
  требует `Start Destroy` перед `Stop Destroy`.
- **2026-11-18.** Замер, который меняет планы: правки блоков сервер возвращает (3 `Block
  Update` за сеанс) — в выживании мгновенное ломание не проходит. Значит следующий крупный
  шаг — не «больше блоков», а удержание ЛКМ с прогрессом и хотбар.
- **2026-11-18.** Игра вылетала, когда игрок улетал: сервер кикал за полёт
  (`Flying is not enabled on this server`), клиент молча умирал. Причина смерти — `send` из
  игрового цикла бросал исключение после разрыва. Теперь кик виден окном и записью в
  `ultracraft-error.txt`, полёт разрешён только при бите `mayFly` из `Player Abilities`,
  ключи причин переведены. Проверено: кик дублирующим входом — клиент печатает причину и
  закрывается штатно; попытка полёта в выживании — отказ без кика.
- **2026-11-18.** Наш `yaw`/`pitch` зеркальны протокольным — на провод пошёл обратный знак.
  Это была реальная ошибка (сервер выбирал другой блок своим `pick()`), но `Mismatch in
  destroy block pos` она не вылечила: остальное — в долгах, до прогресса разрушения.
- **2026-11-18.** «Не всё рендерится»: у мешей появились тесты (`app/src/test`, геометрия без
  GPU), и первый же тест показал, что блок на границе чанка теряет внешние грани, пока сосед
  не загружен. Плюс вторая, более грубая причина: мёртвый игрок не получает чанков вообще.
  Обе исправлены; скриншоты для сравнения снимаются через `--demo --frames`. Что именно
  увидел игрок в тот раз — до конца не подтверждено, поэтому в отчёте честно: причина
  найдена и устранена, но если дыры вернутся, нужны условия (где именно и когда).

## Как поддерживать эту память

- Обновлять после каждого этапа, а не «когда-нибудь»: цифры и ограничения устаревают
  быстрее кода.
- Записывать **почему**, особенно если решение выглядит странным: именно его захочется
  «улучшить» обратно.
- Числа брать из реальных запусков, а не из головы. Оценки в днях не писать — они уже
  подводили (см. «Честно про оценки» в `docs/START-HERE.md`).
- Ограничения перечислять честно: список долгов — это карта, а не признание.

## Стиль кода

- Kotlin, JVM 21, без фреймворков; исключения — `ProtocolException`/`AuthException`.
- Комментарии и пользовательские строки — по-русски; идентификаторы — по-английски.
- Числовые ID пакетов — только в `Protocol777`.
- Никаких синглтонов и глобального состояния: зависимости через конструктор.
- Всё, кроме `app/gl`, обязано работать без окна и иметь тесты.
- В `app/gl` GL-вызовы только в главном потоке.
